## 1. Benchmark Methodology

Two benchmark scripts are included:

- **`scripts/benchmark.js`**: Repeated single-flow synthetic PCAP (HTTP GET, port 80, `github.com`). Measures raw parser throughput with no classification variance across packets.
- **`scripts/benchmark-mixed.js`**: Mixed synthetic traffic fixture generated by `tests/helpers/traffic-fixture.js`, containing TLS, DNS, HTTP, and ICMP-like flows that exercise all branches of the DPI engine and classification pipeline.

All benchmarks run in **offline mode** (sequential single-threaded packet loop), with rules file loaded from a temporary directory. Timing uses `performance.now()` from Node.js `perf_hooks`, wrapping `spawnSync` of the C++ engine binary.

> [!IMPORTANT]
> All elapsed times include process startup time (dynamic linker, Npcap DLL loading, memory allocation). For the 1,000-packet case, startup overhead (~500 ms) dominates the measurement. This explains the apparent non-linear throughput scaling.

## 3. Analysis of Throughput Scaling Behavior

### The Startup Overhead Effect

The benchmark results exhibit strong **sub-linear throughput growth** at small workloads. This is not an algorithmic complexity issue. It is a consequence of fixed system-initialization costs that dwarf the actual packet-processing time at small scales:

| Overhead Source | Approximate Time |
|---|---|
| Process creation & dynamic linker | ~150–200 ms |
| Npcap DLL loading (`wpcap.dll`) | ~100–150 ms |
| WFP library initialization (`fwpuclnt.dll`) | ~50–100 ms |
| rules.json file I/O and parsing | ~10–30 ms |
| output.json final write | ~20–50 ms |
| **Total fixed startup overhead** | **~350–550 ms** |

This overhead is amortized over the packet count. At 1,000 packets, startup dominates: effective processing is only ~50 ms of the total ~554 ms elapsed. At 100,000 packets, the fixed overhead (~400 ms) represents ~40% of total elapsed time, with genuine packet processing accounting for the remainder.

### Corrected Per-Packet Processing Rate

Subtracting the fixed startup overhead (conservatively estimated at 450 ms):

| Workload | Total Elapsed | Est. Processing Time | Effective Packets/s |
|---|---|---|---|
| 1,000 | 554 ms | ~104 ms | ~9,615 |
| 10,000 | 564 ms | ~114 ms | ~87,719 |
| 50,000 | 547 ms | ~97 ms | ~515,464 |
| 100,000 | 1,063 ms | ~613 ms | ~163,131 |

### Why the Paper's Reported Numbers Were Different

The original paper reported: 1,000 pkt → 1,718 pkt/s; 10,000 pkt → 15,998 pkt/s; 100,000 pkt → 46,510 pkt/s.

These were measurements from a different machine configuration (likely lower-speed storage or earlier build). The verified reproducible measurements on the current hardware with the current build are systematically **higher**, which is favorable. The paper must report measurements from the actual test environment, not from a hypothetical baseline.
